# 中信信用卡 Email 補記｜Matt 的產品需求（2026-10-07）

狀態：使用者確認的產品方向／Codex 開發輸入；**不是**正式信箱、OAuth、排程、production DB 或部署授權。

參照：GitHub Issue #57（單一工程 owner 與安全交接）、PR #56（Phase 2 現有規格及未完成關卡）、`docs/ctbc-email-import-phase-2-spec.md`（以 PR #56 最新 head 為準）。本文件補充使用者工作流程；若與 Phase 2 的權限、隱私、RLS、保留期限、不可自動入帳等安全要求衝突，先停下提出差異，不得以本文件降低安全門檻。排程 07:00 與本文件的晚到信觀察衝突，須明確修訂、驗證，不可同時當作有效設計。

## 1. 要解決的痛點與成功體驗

Matt 有時忘記手動記帳，或手動金額與中信刷卡通知有差異。長門逐筆在 Telegram 提問會造成等待；訊息也可能被忽略。希望長門在背景做唯讀搜尋、解析、比對與分類建議，把疑似漏記／有疑問的項目放進 Lite YNAB 網頁的**持久待確認收件匣**。Matt 何時有空就一次進頁面處理，不必等 Agent 一題一題回覆。

成功體驗：首頁或設定有清楚入口與待處理筆數；進入手機可用的頁面後，優先看到最需要決策的候選，一眼辨認日期、金額、商家或「商家未明」、建議類別與支付方式、可能對應的既有交易及警告。可單筆操作或安全地批次處理；處理完待辦數隨之更新。Telegram 僅做一則簡短摘要與入口，不是處理狀態的 source of truth；漏看通知也不會失去候選。

## 2. 第一版邊界

- 僅中國信託寄送的「信用卡消費成交回報」，且僅限經受保護設定指定的一張卡；同封其他正卡、附卡或其他卡的交易列不得進 staging、API、日誌、遙測或個人帳本。不要把真實卡識別值放在 GitHub／spec／fixture。
- 以 Email 的逐筆授權通知作「可能需要補記」線索，不把通知等同已成功請款或月結；通知金額、商家及外幣結算可能改變，退款可能另行反映。月結帳單核對是後續獨立階段。
- 第一版不登入網銀、不處理其他銀行、不解析月結 PDF；不自動確認、入帳、改寫既有交易或刪除正式記帳。除非本人按下確認，候選不進個人預算／交易列表／報表。
- Agent 可建議，不得代理使用者做財務／工作分類的最終判斷。

## 3. 每日收集與時間語意

近期唯讀觀察：這類日報多在消費次日的上午至下午送達，不是刷卡後即時 Email；觀察值不是銀行服務保證。現有 Phase 2 草案的「07:00 掃昨天」通常早於這封日報到達，不能據此聲稱昨天已查完。

產品期望：每天台北時間**約 17:00** 做一次正式收集，主要處理前一台北曆日的消費；重疊回看最近數個已過去曆日以補抓晚到通知，靠來源身分去重，同一 logical run 的失敗重試不得變成第二次日常排程。Codex 必須在 PR #56 更新以台北時間計算的收信時間窗、交易發生日篩選、跨日／假日／延遲／重試／超窗警示的合成測試；若 17:00 無法由實際排程機制可靠實現，提出有證據的替代，而不是默默沿用 07:00。

「沒有收到信」、「排程未跑」、「部分解析失敗」與「確實掃到零筆候選」須分別顯示。即使本次無候選，也只表示**未找到符合條件通知**，不能表示沒有消費或帳已核對完整。超過回看窗口才到的資料須有告警及受控補捕路徑，不能默默遺失、也不自行擴大讀全信箱。

## 4. 比對與建議

- 以本人既有 Lite YNAB 交易為比對對象，先比對日期（含跨日容差）、金額與同一付款來源；商家名稱僅供輔助。對同額同日、金額不同、商家不明等情況，顯示「可能已記過／金額需核對」與候選對應項目，由本人判斷；**不能只憑日期與金額自動判為重複**。
- 建議 Lite YNAB 分類與支付方式時，顯示建議原因（例如本人過去對此商家的分類）及不確定提示；建議可一鍵採用或改選，但不可預設為已批准。資料不足時顯示「請選擇」，不要假裝知道商家。
- 正卡／附卡、付款來源需正確區分；候選資料只顯示必要、已淨化的資訊，遵循 Phase 2 不持久化末四碼／raw Gmail message ID 的安全邊界。
- 解析、建議、去重是三件事：同一來源重掃需防重；不同來源信同一筆或使用者手記則標衝突提示；不能無證據自動消除真實的兩筆相同消費。

## 5. 收件匣畫面與五種處置

頁面位置可沿用 Phase 2 規格的 `/settings/email-import`，另從首頁提供明顯的「待確認交易 N 筆」入口；不把所有 Email 候選混入正式交易清單。每筆提供日期時間、金額、商家（未明則明示）、卡產品／正附卡的非敏感表示、建議類別與支付方式、警告／可能對應既有交易、通知與月結未核對狀態。

使用者可做且語意不可混淆：

1. **補記私人支出**：本人選擇其帳戶內有效分類與支付方式，明確按確認後原子新增**一筆**正式交易；雙擊、重試、分頁競態不得多記。顯示成功結果。
2. **已記過**：本人指定一筆自己既有的交易作連結；不新建第二筆，也不自動改／刪原交易。候選以可追溯的已處理狀態結束。
3. **忽略**：明確選擇不補記並結束此候選；與「已記過」不同，需保留最小去重／處理狀態。
4. **稍後處理**：本次不操作，候選仍維持待確認、仍計入待處理數，下次進入收件匣仍可處理；不得當作忽略、已記過、終態或延長既定保留期限。不強迫對話式逐筆回答。
5. **工作支出／排除個人帳**：終態，不建個人交易，不能流入個人預算、交易列表、分析、報表、CSV／備份；已匯入的正式交易不得因事後按工作支出而隱式刪除。

批次操作只允許使用者**明確勾選**的可安全處理候選（例如同分類／同支付方式的普通候選）；提交前顯示所選筆數與動作。可能重複、金額不符、商家未明、解析警告、工作／私人歸屬不明與版本衝突不得靜默混入批次批准，應單筆確認或阻擋並說明。沒有「全部自動批准」。

首頁與收件匣需處理：載入中、尚未成功執行過、零候選、部分失敗、晚到、解析失敗、缺分類／付款方式、衝突、雙擊提交、跨分頁 stale version、成功／排除回饋。手機窄版與鍵盤操作可用；中文採台灣用語。待處理筆數以可操作 pending 為準，不把已忽略／已記過／已排除的筆數算進去。

## 6. 長門與通知分工

長門／collector 做背景讀取、解析、比對、建議與失敗告警，不在 Telegram 用「你要把這筆歸哪類？」逐題輪詢。Telegram 可在一次日掃完成後給一則「新增待確認 X、金額／重複疑問 Y、資料失敗 Z」的摘要及收件匣入口；對於沒有明確推送權限或可靠通道的環境，先保證網頁待辦持久可見，通知為次要便利功能。不可把私密交易明細、卡別識別值、原始郵件轉貼到公開平台或公開 GitHub。

## 7. 資料、權限、保留與上線邊界

沿用 PR #56 的 Gate A–D：先合成資料純邏輯與隔離資料庫／RLS，再無真信箱／無正式寫入的 UI 預覽，之後另經授權才碰真實 Gmail、受保護卡設定、正式 staging、排程與 production 寫入。正式 collector 須嚴格驗證銀行來源與可信 Gmail 驗證 header，server 端固定 owner 並先逐列過濾目標卡；瀏覽器 RLS 與狀態變更驗證本人 ownership、版本／並發／冪等。Gmail 唯讀；不存原信、完整／部分卡號、raw message ID、token、Email header 或可反查指紋；Log 僅無個資聚合／錯誤碼。保留期限與清除流程以 PR #56 現有 30／7／90 天規格為基線，變更另提理由與 gate。

目前已知 `S8-PROD` 未完成、`BLOCKED_NO_APPLY`，S9 production-bound implementation 不可因此文件被放行。文件、合成 fixture、隔離 prototype 與驗證可以先推進；production migration/history repair、真正收信、OAuth/env/secrets、排程啟用、正式資料寫入、部署／服務操作均各有獨立精確授權／驗證門檻。沿用 #57 的 Codex 單一工程 writer，避免另一代理同時改同一 branch。

## 8. 可驗收情境（至少）

- 合成混合卡信：只產生受保護指定卡候選；非目標列不入 API／DB／log；仿冒寄件者或驗證失敗不入候選。
- 07:00 尚未寄信、17:00 寄達、隔日／跨假日晚到、部分成功／部分失敗、逾窗信、同一信重掃：時間窗與提示正確，不重複，不宣稱完整。
- 已手記同額同日／跨日、同商家不同金額、相同兩筆真實消費：只給人工判斷／衝突，不能誤消除或重記。
- 本人明確確認私人支出後一筆正式交易；雙擊／重試／跨分頁競態仍一筆；分類或付款方式不屬本人／被刪則阻擋。
- 已記過只連既有交易；忽略為不同終態；稍後仍 pending；工作排除不進任何個人帳本與匯出；錯誤的事後工作標籤不會刪已匯入交易。
- 批次不夾帶風險筆；手機與鍵盤可完成五種處置；待辦數、通知摘要與失敗狀態一致；收件匣未開啟前使用者仍可之後回來處理。
- 合成資料測試、parser/去重/RLS/RPC/候選 UI/隔離網路 spy、lint/typecheck/test/build、獨立審查／UX QA 依 Tier 2 gate 執行；宣稱「已上線」前另需正式授權、部署證據及精確讀回。
